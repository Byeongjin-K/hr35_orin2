# LiDAR ↔ ZED X 외부 파라미터 보정 — 현장 실험 절차

> **2026-08-13 개정 — 대상 카메라가 붐에서 캐빈으로 바뀌었다.**
> 붐 하단 카메라는 각도상 버킷이 닿는 작업영역을 대부분 보지 못해 캐빈 상단
> 카메라(SN 49749405)로 교체했다. **이건 토픽만 바뀌는 변경이 아니다** — 기구학
> 구조가 바뀌어 보정 설계 자체가 달라진다. 아래 0-2절을 먼저 읽을 것.

## 0-1. 왜 이게 선택이 아닌가

TF 트리에서 카메라만 고아다.

```
map ─┬─ gm_swing_axis / gm_boom_hinge / gm_boom_link / gm_lidar_mount / gm_os_lidar
     └─ lidar_boom/os_sensor ─ lidar_boom/os_lidar

zedx_cabin_camera_link ─ … ─ zedx_cabin_left_camera_optical_frame   ← 어디에도 안 붙음
```

`map` 좌표를 픽셀로 옮길 경로 자체가 없으므로, 보정 없이는 AR 오버레이의 모든 산출물이
"그럴듯하지만 틀린 그림"이 된다. `excavator_description/urdf/excavator.urdf`에는
카메라 링크가 아예 없어서 도면에서 뽑아낼 수도 없다.

## 0-2. 카메라와 LiDAR는 강체가 아니다 【가장 중요】

카메라는 **캐빈**에, LiDAR는 **붐**에 있다. 붐이 움직이면 둘 사이 변환이 바뀜다.
동일 시각 실측(2026-08-13):

```
gm_swing_axis   pitch  -4.68 deg     gm_boom_hinge   pitch  -4.74 deg   ← 캐빈 강체
gm_boom_link    pitch -44.25 deg     gm_lidar_mount  pitch -44.20 deg   ← 붐 강체
```
같은 날 오전엔 붐 프레임이 -31.9도였고 오후엔 -44.2도다. **12.3도 움직였다.**

따라서:

* 이전 절차의 전제였던 "두 센서가 한 브래킷에 있으니 |t| < 0.6 m"는 **무효**다.
* 구해야 하는 것은 `T_camera ← lidar` 가 아니라 **`T_camera ← gm_swing_axis`** 다.
  이것만이 상수다.
* 부수적 이득이 크다: dig 셀이 이미 `gm_swing_axis`에서 계산되므로 셀→픽셀이
  **상수 변환 하나**로 줄고, 붐 기구학 오차가 오버레이로 아예 새지 않는다.
* 대가: LiDAR를 기준 센서로 쓰려면 매 캡처의 **붐 각도를 기구학 체인으로 통과**시켜야
  하므로, 붐 각도를 바꿔가며 받는 캐프처가 교차검증용 옵션이 아니라 **필수**가 된다.

## 0-3. 선행 조건 — LiDAR 프레임 이중화를 먼저 가려야 한다

클라우드를 카메라로 옮기려면 `lidar_boom/os_lidar → map → gm_swing_axis → camera`를
거치는데, 첫 구간이 bringup 하드코딩 placeholder다(A절 밖, live_work_plan B항).

2026-08-13에 두 체인을 오버레이로 직접 비교해 봤으나 **가릴 수 없었다**:
placeholder는 800점이 좌하단에 몰리고 기구학(`gm_os_lidar`)은 13442점이 상단을 덮는데,
카메라 외부 파라미터가 미보정이라 **두 오차가 섞여 분리되지 않는다.**

그러므로 B는 카메라와 무관하게 먼저 풀어야 한다 — 붐을 스윈하며 **맵 프레임에서 본
지면 평면 높이가 붐 각도에 의존하면 안 된다**는 불변량을 쓴다.
스크립트는 이미 있다: `~/repos/ontariotech_koceti_jetson_docker/gridmap_diag/calib_a_lidar.py`.
다행히 그 판별에 필요한 데이터는 아래 4-3의 붐 각도 캐프처와 동일하다.

순서: **B(체인 판정) → A(카메라 보정)**. 반대로 하면 A가 B의 오차를 흥수해버린다.

## 1. 필요한 정확도 (요구치 역산)

| 항목 | 값 | 근거 |
|---|---|---|
| grid 셀 | 0.15 m | AI/GUI 공통 규약 |
| 판정 기준 | 셀의 1/2 = 0.075 m | 이보다 크면 인접 셀과 구분 불가 |
| 대표 굴착 거리 | 약 6 m | 붐 카메라 시야 |
| **필요 회전 정확도** | **≤ 0.72°** | 6 m에서 0.075 m를 만드는 각도 |
| **필요 병진 정확도** | **≤ 0.075 m** | 거리 무관, 직접 오차 |
| 목표치 (여유 2배) | **0.3° / 0.03 m** | 아래 절차로 도달 가능 |

눈대중 정렬은 보통 1~2°에 머문다. 6 m에서 **10~20 cm, 즉 셀 1개 이상** —
정확히 이 프로젝트가 잡아내려는 오차와 같은 크기다. 그래서 타겟이 필요하다.

## 2. 장비 사양 (타겟 크기의 근거)

| | 값 |
|---|---|
| ZED X (발행 해상도) | 1280×800, fx=fy=845.49, HFOV 74.2°, VFOV 50.6°, **0.0678°/px** |
| Ouster OS-0-128 `512x10` | 512 col × 128 beam, VFOV 90.3°, **0.703°/col × 0.706°/row** |

LiDAR가 카메라보다 **약 10배 거칠다.** 이게 정밀도의 병목이므로 타겟은
"LiDAR 점이 충분히 찍히는 크기"로 정해야 한다.

| 거리 | LiDAR 점 간격 | A0 보드(84×119 cm)에 찍히는 점 |
|---|---|---|
| 3 m | 3.7 cm | 22 × 32 |
| 5 m | 6.1 cm | 13 × 19 |
| 8 m | 9.8 cm | 8 × 12 |
| 10 m | 12.3 cm | 6 × 9 |
| 15 m | 18.4 cm | 4 × 6 ← 너무 적음 |

**결론: A0 보드, 타겟 거리 3~8 m 유지.**

## 3. 준비물

- **A0 체커보드** (84×119 cm) — 평평하고 휘지 않는 판(합판/포맥스)에 부착.
  칸 크기는 **10 cm 이상**, 내부 코너가 최소 7×9. 실제 인쇄된 칸 크기를 **자로 재서 기록**할 것
  (인쇄 배율 오차가 그대로 스케일 오차가 된다).
- 보드를 세워둘 삼각대 또는 이젤. 사람이 들고 있어도 되지만 **20초 동안 안 움직여야** 한다.
- 줄자.

체커보드가 없다면 4절을 건너뛰고 6절(대안)을 볼 것.

## 4. 본 실험 — 보드 자세 8~10개

### 4-1. 사전 (5분): 거친 정렬로 초기값 확보

```bash
ros2 launch excavator_ar_overlay lidar_projection.launch.py
# /excavator/perception/dig_overlay/compressed 를 rqt_image_view 등으로 띄워놓고
ros2 param set /lidar_projection_node extrinsic.rpy "[-1.5708, 0.0, -1.5708]"
ros2 param set /lidar_projection_node extrinsic.xyz "[0.0, 0.0, 0.0]"
# 문틀·기둥 같은 수직 엣지가 대충 맞을 때까지 rpy/xyz 를 흔들어 본다
```

정밀할 필요 없다. **최적화가 수렴할 초기값**만 만들면 된다. 이 값을 적어둘 것.

### 4-2. 캡처 (25분)

각 자세마다:

```bash
src/excavator_ar_overlay/scripts/record_calib_capture.sh pose01 20
```

**자세를 고를 때 지켜야 할 세 가지.** 이걸 어기면 데이터가 아무리 많아도 해가 안 풀린다.

1. **거리를 벌릴 것 — 최소 3개 구간 (3 m / 5 m / 8 m).**
   모든 타겟이 같은 거리에 있으면 회전과 병진이 서로를 흉내 낸다(축퇴).
   카메라를 좌로 1° 돌린 것과 우로 몇 cm 옮긴 것이 같은 그림을 만든다.
2. **화면을 채울 것 — 좌/중앙/우 × 상/하.**
   중앙에만 모이면 주점 근처라 렌즈 기하 정보가 거의 없다.
3. **보드를 기울일 것 — 정면에서 20~40°, 기울기 방향도 자세마다 바꿀 것.**
   항상 정면이면 보드 법선이 한 방향뿐이라 평면 구속이 부족해진다.

추가로:
- 보드 **앞뒤로 1 m 이상 빈 공간**을 둘 것. 벽에 붙여두면 LiDAR가 보드와 벽을 한 덩어리로 본다.
- 캡처 20초 동안 **붐·기계·보드·사람 모두 정지.**
  (Ouster는 센서 uptime, ZED는 epoch로 타임스탬프를 찍어 두 스트림을 시간 정렬할 수 없다.
  정지 장면이면 이 문제가 사라진다.)

### 4-3. 붐 각도 변경 캡처 【교차검증이 아니라 필수】 (10분)

**붐 각도를 3개 이상으로 바꿔가며** 위를 반복한다. 각도당 자세 3개.
가능하면 붐을 크게 벌려놓은 것·중간·접은 것으로 범위를 넓게 쓸 것.

이전 판(붐 카메라)에서는 이게 "값이 흔들리는지 보는" 교차검증이었다. 지금은 다르다:
카메라(캐빈)와 LiDAR(붐)가 강체가 아니므로 매 캡처마다 둘 사이 변환이 실제로 다르고,
**그 차이를 만드는 것이 바로 붐 기구학 체인**이다. 따라서 붐 각도 다양성이 없으면
`T_camera ← gm_swing_axis` 가 체인 오차와 분리되지 않는다. 거리 다양성과 같은
이유로 필수이며, 빠지면 해가 안 풀린다.

부가 이득: 이 데이터는 0-3절의 B항 판정(지면 높이의 붐각 무의존성)에 그대로 쓰인다.

## 5. 현장에서 바로 하는 합격 판정

캡처가 끝나면 그 자리에서:

```bash
ros2 param set /lidar_projection_node lidar.point_radius_px 1
ros2 param set /lidar_projection_node lidar.far_m 10.0
```

오버레이에서 **보드 윤곽에 LiDAR 점의 깊이 불연속이 걸쳐 있는지** 본다.
현재(미보정) 상태에서는 출입구 같은 원거리 영역이 근거리 색으로 찍히는 것이 육안으로 보인다.
보정 후 이게 사라지면 성공.

## 6. 체커보드가 없을 때 (대안)

정확도는 떨어지지만(약 0.5~1°) 장비 없이 가능하다.

- 깊이 불연속이 강한 **자연 구조물**을 쓴다: 건물 모서리, 문틀, 전신주, 주차된 차량, 컨테이너 모서리.
- 3~8 m 범위에 그런 대상이 좌/중/우로 흩어져 보이는 위치에 기계를 세운다.
- 4-2와 같은 방식으로 붐 각도 3개 × 20초 캡처.
- 오프라인에서 엣지 정렬 최적화(Levinson-Thrun 방식)를 돌린다. 4-1의 초기값이 필수다.

## 7. 캡처 후

번들을 그대로 넘겨주면 된다. 오프라인에서:

1. 카메라: 체커보드 코너 검출 → 보드 자세(카메라 프레임)
2. LiDAR: 보드 평면 분할 + 평면 적합 → 보드 평면(LiDAR 프레임)
3. 두 관측이 일치하도록 6-DoF 최적화 → `T_camera ← lidar_boom/os_lidar`
4. 자세를 학습/검증으로 나눠 교차검증, 잔차 리포트
5. 결과를 `extrinsic.xyz` / `extrinsic.rpy`에 넣고, 확정되면
   `static_transform_publisher` 또는 URDF로 이관 (`publish_static_tf: false`)

## 8. 같이 풀어야 하는 문제 — LiDAR 프레임이 두 개다

```
map → gm_os_lidar            [2.209, 0.065, 2.113]   붐 기구학 (붐 따라 움직임)
map → lidar_boom/os_sensor   [0, 0, 2.0]             bringup 하드코딩 placeholder
두 프레임 차이: 2.141 m, yaw 17.2°
```

포인트클라우드는 **placeholder 쪽**에 매달려 있다
([boom_only_driver.launch.py:79](../../hr35_bringup/launch/boom_only_driver.launch.py)의
`'0','0','2','0','0','-1.5708'`).

7절의 보정은 센서↔센서 직접 변환이라 이 문제와 무관하게 풀린다. 하지만 grid map(`map` 프레임)을
카메라로 투영하려면 카메라를 **기구학 체인**에 붙여야 하므로, 어느 쪽이 물리적으로 맞는지
확정해야 한다. 판별 실험은 이미 있다 — 붐을 스윕하며 지면 평면 높이가 붐 각도에
의존하는지 보는 `gridmap_diag/calib_a_lidar.py`. 위 4-3의 붐 각도 캡처가 이 검증에도 그대로 쓰인다.
